# Surfaces

Status: approved-design

## Context

This is the second of two sub-projects that improve the app's UI/UX flow. The first, specified in
`2026-07-26-learning-engine.md`, rebuilt the drill rules and the progress data model: `LineDrill`,
`LessonRunner`, `review-schedule.ts`, `mastery.ts`, and per-position progress records. That work is
complete and browser-verified.

This project builds the screens that display that data, and adds the engine that explains why a
move is wrong. It covers four things: the dashboard redesign with line-level progress and overall
mastery, a cross-course review queue screen, a browse/study page, and an evaluation bar backed by a
Stockfish WASM worker. A third, separate project expands course content with additional variations
and lines.

Two constraints carry forward.

`release-readiness.test.ts` scans every `.css`, `.json`, `.rs`, and `.ts` file under `src/` and
`src-tauri/` and asserts the source never matches
`/fetch\s*\(|xmlhttprequest|pgn|offline|course.?editor|apk/i`. The engine must therefore load
without a literal `fetch(` in our own source. The design below satisfies this without editing the
guard, and the guard must not be edited.

`mastery.ts` already exports `courseMastery` and `overallMastery`, and `overallMastery` has no
caller yet. The dashboard header is its consumer. Mastery is never recomputed by hand anywhere in
this project; every figure and meter reads from these two functions or from the shared line-state
predicate described under Dashboard.

## Problem

The learning engine produces line-level banking, per-position review state, and a mastery figure.
No screen shows any of it.

**The dashboard shows level counts only.** A course card reports `01 / 03` levels completed. It
says nothing about which of the three lines in a level are banked, which hold due positions, and
nothing at all about mastery across the repertoire. A learner cannot tell where the weak spots are.

**Review is scattered and per-course.** Review entry points are per course and per level, computed
inline in `renderDashboard` and rendered twice: once in the card footer, then again by an
`insertAdjacentHTML` pass that re-derives the same position ids with different labels. There is no
single answer to "what should I review right now", and reviewing across four courses means finding
and starting four separate sessions.

**Lines can only be reached through a test.** The only way to see a line is to be drilled on it,
and only if its level is unlocked. There is no way to read a line's moves and explanations before
or after practising it.

**Wrong moves are still unexplained.** Feedback names the expected move and restates the position's
authored plan, but never says what the played move actually cost. The learning-engine spec
deliberately left this to the evaluation bar.

One structural problem makes all of this harder. `main.ts` is a single 38KB module holding
authentication, every screen, the board renderer, pointer input, animation, and save orchestration.
The browse walker needs the board renderer, and the evaluation bar needs to render beside the board
on two screens, so shared extraction is unavoidable. Adding three screens to the file as it stands
would make the same split significantly more expensive later.

## Goals

- Keep the vanilla TypeScript architecture, Firebase progress model, course content, and visual
  identity.
- Split `main.ts` into per-screen modules over a shared shell and a shared board view, moving the
  practice screen without changing its behaviour.
- Show line-level progress and overall mastery on the dashboard.
- Give the whole repertoire one review queue, with a single action that runs every due group.
- Let any line be read move by move, with its explanations, whether or not it is unlocked.
- Show an engine evaluation beside the board, and say what a wrong move cost.
- Degrade cleanly and completely when the engine cannot start.

## Out of Scope

- Any change to course content, lesson order, or the number of variations per lesson.
- Any change to the drill rules, review scheduling, mastery definition, or progress schema from the
  learning-engine project.
- Any change to authentication or Firestore rules.
- A new router, state-management layer, component framework, or design system.
- Editing the `release-readiness.test.ts` token guard.
- Free exploration from a browsed position, which the learning-engine spec already declined. The
  walker replays authored lines only.
- Free-text search on the browse index. Thirty-six rows do not need one; the filter chips are
  enough.
- Engine analysis features beyond a single evaluation per position: no principal variation display,
  no multi-line output, no opening book, no engine-versus-learner play.
- Named line detail on the dashboard. It lives on the browse index.
- Any change to the sources page beyond the topbar it shares.

## Architecture

`main.ts` keeps only the authentication watcher and a `navigate(screen, params)` dispatcher, which
it passes into each screen render as a callback. Screens therefore never import each other and the
import graph stays acyclic.

```
src/main.ts                  auth watch + navigate dispatch
src/screens/shell.ts         topbar, settings dialog, escapeHtml, scroll reset
src/screens/dashboard.ts
src/screens/review-queue.ts
src/screens/browse.ts
src/screens/practice.ts      moved verbatim from main.ts
src/board-view.ts            renderBoard, renderRoute, squareName, squarePosition, markerPosition
src/review-queue.ts          pure: aggregate due positions across all courses
src/engine/engine-client.ts  worker lifecycle, one evaluation in flight
src/engine/eval-scale.ts     pure: centipawns to bar geometry, label, severity
public/engine/               vendored single-threaded Stockfish WASM and glue
```

### `screens/practice.ts`

`startPractice` and its helpers move out of `main.ts` unchanged except for imports and the two
additions this project makes: the evaluation bar and the review-run continuation. The move is
otherwise verbatim. `learning-engine.spec.ts` passing unedited is the evidence that behaviour did
not change.

### `screens/shell.ts`

Holds what every screen shares: `escapeHtml`, `resetPageScroll`, the topbar markup with its account
controls, and the settings dialog with its binding. The topbar takes which links to show, so the
dashboard can offer Browse and Sources while practice offers Dashboard and the sources page keeps
its back button.

### `board-view.ts`

The pure-markup half of the current board renderer: `renderBoard`, `renderRoute`, `squareName`,
`squarePosition`, and `markerPosition`. Pointer input, drag lift, and animation stay in
`screens/practice.ts`, because the walker has no input and no animation. `renderBoard` already takes
a `disabled` flag, which the walker uses.

### `review-queue.ts`

Pure. Given `COURSES` and progress by course, returns the due groups and the total. No DOM, no
Firestore.

### `engine/`

`engine-client.ts` owns the worker and the UCI conversation. `eval-scale.ts` is pure and owns every
number the bar and the cost line display.

## Engine Delivery

The engine ships as a vendored single-threaded Stockfish WASM build in `public/engine/`, loaded with
`new Worker('/engine/stockfish.js')` and driven over UCI with `postMessage`.

A single-threaded build is required: a multi-threaded build needs `SharedArrayBuffer`, which needs
COOP and COEP response headers that Firebase Hosting is not currently configured to send. Vite
copies `public/` into `dist/` verbatim, and `src-tauri/tauri.conf.json` already points
`frontendDist` at `../dist`, so the same asset serves the web build and the desktop build with no
extra build step. Because the asset is local, engine availability does not depend on the network.

This also satisfies the token guard without touching it. The guard reads only `.css`, `.json`,
`.rs`, and `.ts` files under `src/` and `src-tauri/`, so the vendored glue code's internal `fetch(`
is never scanned, and our own client constructs a `Worker` rather than fetching anything.

## Dashboard

### Overall mastery

The intro block gains the figure from `overallMastery`: mastered lines out of the repertoire total
as a percentage, with a one-line reading of what mastered means, which is banked with nothing in it
due. The denominator comes from `COURSES`, so it rescales when the content project adds lines.

### Review entry

One entry point replaces the current review links: a single control reading `Review N positions`
that opens the review queue screen, where N is the cross-course total. It is absent when nothing is
due. Both existing review-link paths are deleted, including the `insertAdjacentHTML` pass that
duplicated them.

### Course cards

Each card keeps its side tag, name, description, core line, three level rows, and the `01 / 03`
count of levels completed. Each level row gains a three-segment meter, one segment per line, in one
of three states:

- **untouched** — the line is not in `completedVariationIds`.
- **banked** — the line is in `completedVariationIds` but at least one of its positions is `due`.
- **mastered** — the line is banked and none of its positions is `due`.

A shared predicate in `mastery.ts` returns the state for a line, and `courseMastery` counts the
mastered ones. The meter and the percentage therefore cannot disagree.

### Topbar

Gains a Browse link beside Sources.

## Review Queue Screen

### Grouping

`review-queue.ts` takes `COURSES` and the loaded progress and returns
`{ courseId: Course['id']; level: LevelKey; positionIds: string[] }[]` in `COURSES` order then
`LEVELS` order, with a total. Groups with nothing due are omitted. It reuses `duePositionIds` from
`review-schedule.ts` and defines no scheduling rules of its own.

### Screen

Each group renders as a row naming the course, the level, and its due count, with its own Review
button that starts exactly the session the dashboard used to start. A primary `Review all` sits
above the rows. When nothing is due, the screen states that everything banked is holding, and the
dashboard hides its entry point.

### Review all

The practice screen accepts an optional review run: the ordered groups plus an index into them.
Each group is its own `LessonRunner` over its own course's progress, so per-course saving works
through the existing `persist` path with no change. Progress is not batched across courses.

On finishing a group, the completion action reads `Next: <course>, <level>` instead of Proceed, and
activating it resets the board to the next group's first position behind the existing named-handoff
state, which now names the incoming course as well as the line. After the last group the action
returns to the review queue, which by then shows its empty state.

The run advances only after the finished group's save resolves, matching how Proceed already waits
on `pendingSave`. A failed save keeps the learner on the completion screen with the existing Retry
Save action, and the run does not advance until it succeeds.

## Browse and Study

### Index

Every line across every course and level, grouped by course then level. Each row names the line,
its `kind`, its move count, its authored `evalCp`, and its state from the shared predicate.

The predicate's middle state, banked with at least one due position, is labelled differently on the
two screens on purpose. The dashboard meter calls it banked, because the meter reads as progress.
The browse chip calls it due, because the index reads as a worklist. Both render the same predicate
result, so they cannot disagree about which lines are in that state.

Filter chips narrow by course, one chip per course plus All, and by state: All, Due, Unbanked, and
Mastered.

### Walker

Selecting a line opens a read-only board. The board squares render disabled through the existing
`renderBoard` flag. Prev and Next controls and the left and right arrow keys step through the
line's positions. Each step shows the expected-move arrow, that position's authored `explanation`,
the move list with the current move marked, and the evaluation bar.

Locked and unbanked lines are fully browsable: reading a line before being tested on it is the
purpose of the page. The walker writes no progress and never constructs a `LineDrill` or a
`LessonRunner`. Stepping changes the displayed FEN instantly in both directions, with no animation.

Its actions are `Practice this level`, shown only when that level is unlocked, and back to the
index.

## Evaluation Bar

### Perspective and scale

Evaluations are always shown from the learner's side, so a positive number means the learner is
better in both white and black courses. `eval-scale.ts` holds every number:

- Fill fraction is `0.5 + 0.5 * cp / (Math.abs(cp) + 400)`, which is smooth, symmetric about zero,
  and saturates gracefully without a clamp.
- A mate score fills the bar for the mating side and labels as `M3`.
- A move's cost falls into four bands: under 50 centipawns is fine, 50 to 149 an inaccuracy, 150 to
  299 a mistake, and 300 or more a blunder.

### Placement

A slim vertical strip beside the board on desktop, becoming horizontal above the board caption at
the existing narrow breakpoint. It fills instantly under `prefers-reduced-motion`.

The bar is `aria-hidden` with its value in adjacent text that is deliberately not a live region, so
a continuously updating evaluation cannot interrupt a screen reader. Only the wrong-move cost
speaks, through the existing polite feedback region.

### Client behaviour

`engine-client.ts` starts the worker lazily on the first evaluation request. One evaluation is in
flight at a time and the latest request wins: superseded requests are dropped and stale `bestmove`
replies are ignored by request id, so stepping quickly through a line cannot leave the bar showing
an earlier position. Each request is `go movetime 300`. Results are memoized per FEN for the
session, so stepping backward and forward through a line is free. Evaluation is requested only after
the board settles, never during an animation sequence.

### Wrong-move cost

When a move is rejected as incorrect, the engine evaluates the position after the played move and
the position after the expected move, and the difference becomes the explanation, phrased with the
severity band, for example `Bd3 gives up 1.4 - Nf3 keeps it level`. The feedback renders
immediately with the learning-engine wording, and the cost line appends when both evaluations
return, so nothing blocks input. Illegal moves are not evaluated.

## Error Handling

The engine is unavailable when the worker fails to construct or when no first result arrives within
three seconds. In that state the bar is absent behind a quiet note, wrong-move feedback keeps
exactly its learning-engine wording, and nothing else on any screen degrades. One retry is
attempted on the next screen entry, never in a loop. Because the asset is local, this path means a
broken build rather than a missing network.

Dashboard, review queue, and browse all load progress for four courses. A failed load keeps the
existing pattern: the error page with its retry action. The browse index needs progress only for its
state chips, so if progress fails there the index still renders its lines with the chips omitted and
a quiet note, because reading a line does not depend on progress.

Practice-screen save behaviour is unchanged from the learning-engine project, including delta
watermarking and Retry Save.

## Verification

### Automated checks

New Vitest coverage:

- `eval-scale.ts`: fill fraction monotonic in `cp` and symmetric about zero, mate handling, and each
  of the four severity boundaries at 49/50, 149/150, and 299/300.
- `review-queue.ts`: grouping in course-then-level order, correct totals, groups with nothing due
  omitted, and the empty result when nothing is due anywhere.
- `engine-client.ts` against a fake worker: latest request wins, stale replies ignored,
  per-FEN memoization issues one request, and a startup timeout yields the unavailable state.
- The shared line-state predicate in `mastery.ts`: untouched, banked-with-a-due-position, and
  mastered.

Existing tests:

- All existing suites pass with no change beyond import paths.
- `learning-engine.spec.ts` and `targeted-ui-repair.spec.ts` pass unedited apart from any selector
  that moved, which is the evidence that relocating the practice screen changed no behaviour.
- `release-readiness.test.ts` passes with the guard unedited.

Also run the production TypeScript and Vite build, the pure Vitest suite, and the Firebase Auth and
Firestore emulator suite.

Playwright stubs the engine by intercepting `/engine/stockfish.js` and serving a fake UCI worker, so
no test hook exists in production code.

### Browser checks

In Chromium at 1440x1000 and 390x844:

1. The dashboard mastery percentage agrees with the segment meters across all four cards.
2. A level with one banked line and one due position shows banked, not mastered.
3. The review entry appears only when something is due, and its count matches the queue total.
4. The queue lists due groups in course-then-level order with correct counts.
5. `Review all` runs two courses back-to-back, naming the incoming course in the handoff.
6. Each group's progress saves to its own course document during the run.
7. Finishing the last group returns to the queue, which shows its empty state.
8. The browse index filters by course and by state.
9. The walker steps with Prev, Next, and the arrow keys, and writes no progress.
10. A locked line opens in the walker, and `Practice this level` is absent for it.
11. The bar reads from the learner's side in both a white and a black course.
12. A wrong move shows its cost after the immediate feedback, without blocking input.
13. With `/engine/stockfish.js` blocked, every screen still works, the bar is absent with its note,
    and wrong-move feedback keeps the learning-engine wording.
14. The bar is vertical at 1440 and horizontal at 390, and does not overflow either.
